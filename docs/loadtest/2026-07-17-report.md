# LLM 治理层负载压测报告

日期: 2026-07-17
环境: 本机(Windows 11),API 单实例(uv run rag-api),mock LLM 替身(loadtest/mock_llm.py,
基线延迟 200ms),PostgreSQL/Redis/MinIO 走 docker compose。
治理配置: CHAT_RPM_LIMIT=60, CHAT_MAX_CONCURRENCY=8, EMBEDDING_RPM_LIMIT=500,
RERANK_RPM_LIMIT=120, ACQUIRE_MAX_WAIT_SECONDS=10, BREAKER_FAILURE_THRESHOLD=5,
BREAKER_COOLDOWN_SECONDS=30, LLM_TIMEOUT_SECONDS=60, EMBEDDING/RERANK_TIMEOUT=30。
压测工具: Locust headless,完整读取 /chat/ SSE 流;对账数据来自 llm_call_log(服务端逐次记录)。

> 延迟口径说明:Locust 的响应时间只计到 SSE 响应头返回(P50 ≈ 4ms 为伪影),
> 本报告的延迟一律取 llm_call_log 的 latency_ms(逻辑调用端到端)。

|---|---|---|---|---|---|
| S1 基线 | 5 用户 / 2min / mock 200ms | 76 | 3.95% | 1847ms / 6638ms | 通过:限流仅削峰(见发现 1) |
| S2 限流饱和 | 60 用户 / 2min | 274 | 75.55% | 4348ms(72 成功) | 通过:超额请求 10s 有界等待后友好拒绝,无雪崩,API 全程存活 |

## S3 熔断时间线

- 13:52:33 mock 切换 100% 返 500,locust 起 10 用户
- +1.2s embedding 熔断器打开(opened_at 1784267690.10)
- +2.5s chat 熔断器打开(opened_at 1784267691.37);rerank 同窗打开
- 故障期 70s:303 个请求全部快速失败(客户端 P50 ≈ 5ms),打点分布:
  chat_stream/chat_structured 各 303 rejected(CircuitOpenError)、embedding 606 rejected、
  rerank 7 failed(LLMServerError,熔断打开前的真实失败)+ 296 rejected
- 13:53:46 mock 恢复健康,重新加压 90s
- 冷却期(30s)残余 CircuitOpenError:chat 5、embedding 7、rerank 2,随后探针成功、
  熔断闭合(Redis 中 open 状态被删除,仅剩 failures=0),58 个 chat_stream 成功
- **零穿透验证**:故障期熔断打开后,mock 侧不再收到任何请求打点

## S4 慢供应商

- mock 延迟 70s;管道首个外呼是 embedding(30s 超时):第一波 5 个并发 embed 在
  ~30s 齐超时 → 5 次失败瞬间达到阈值 → **embedding 熔断打开**(rejected avg 31.9s)
- 随后 chat_structured 在 60s 超时后同样把 **chat 熔断器**推开(failures=9),
  4 个改写调用以 CircuitOpenError 终止(avg 108s = 首次 60s 超时 + 退避 + 二次 acquire 被熔断拒绝)
- 客户端(locust)2 分钟窗口内 0 个请求完成——慢供应商事故的用户体验:首分钟挂起,
  之后熔断快速失败
- **坑位无泄漏**:压测结束后 30s 内,5 个 chat 并发坑位随服务端调用自然结束经 finally
  全部释放(ZCARD 归零),僵尸清理(3×timeout 阈值)未误清活跃调用

## 发现与调参建议

1. **每个用户请求消耗 2 次 chat 配额**(查询改写 chat_structured + 生成 chat_stream 共享
   chat 桶)。CHAT_RPM_LIMIT 须按 2× 目标请求率核算:支撑 30 请求/分钟需要 RPM≈60。
   后续可考虑给改写调用独立配额桶或独立倍率。
2. **滑动窗口为两桶加权近似**,持续饱和下实测放行超额 ~40%(85/min vs 60)。把配额视为
   "软目标"即可;若需硬上限,应改精确滑动窗口(ZSET 时间戳)并接受额外 Redis 开销。
3. **拒绝前等待 10s 偏长**:交互式 chat 的用户在被拒绝前要等满 ACQUIRE_MAX_WAIT_SECONDS。
   建议交互路径降到 3-5s,让"人数较多请稍后再试"更快到达。
4. **慢供应商场景由 embedding 30s×3 主导**(管道首跳),chat 超时基本不被触达。
   若要收紧故障止损,优先调 EMBEDDING_TIMEOUT/重试次数,而非 chat 侧。
5. **高并发下熔断先于单调用重试耗尽打开**:llm_call_log 中大量终态为 rejected 而非
   failed(尝试级失败计数与逻辑调用级打点的口径差),对账时注意区分。
6. **客户端断连后服务端调用继续跑完**(既有问题,最终代码审查已记录):S4 中坑位被
   已放弃的请求占用直至调用结束。修复方向:stream_chat 消费端断开时 cancel `_produce`。
7. 压测期间 Langfuse/OTel 导出超时刷错误日志,压测环境建议 LANGFUSE_ENABLED=false。
8. mock 保真度修复(96dbb34):json_mode 请求需返回合法 JSON,否则改写节点 3 次重试
   把 chat 配额消耗放大 ~2 倍,基线即饱和——首轮 S1 的 25% 降级即由此产生。

## 结论

四个场景全部达到设计目标:限流有界等待+友好拒绝、熔断快速打开/自动恢复、超时兜底并
级联进熔断、并发坑位无泄漏、被拒调用完整入库可对账。治理层可以开启
(GOVERNANCE_ENABLED=true)投入使用,建议先按发现 1/3 调整 CHAT_RPM_LIMIT 与
ACQUIRE_MAX_WAIT_SECONDS。
